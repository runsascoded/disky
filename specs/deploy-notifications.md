# Shared site deployment notifications

Requested November 10: notify each deployment's admin channel when a site deployment succeeds, fails or is cancelled. HF routes to #hf-admin; GCS, CW and R2 use their corresponding channels. Louisa's deployment rehearsal should have the same visibility as other operators' releases.

## Current state

The shared helper and manual integration below are implemented for review; delivery is disabled. No Slack message, webhook, policy or CI secret has been created or enabled.

## Common receipt and interface

`site/deploy-notify record` records a manual attempt. `render RECEIPT` prints its review copy: the sender name, then the notice's one line. `send RECEIPT` also only renders; posting requires both `send --execute RECEIPT` and `DEPLOY_NOTIFICATIONS_ENABLED=1`, plus `SLACK_DEPLOY_BOT_TOKEN` and `SLACK_DEPLOY_CHANNEL` (the channel's ID). Example receipts live in `site/fixtures/deploy-notices/`. The unposted editable Slack drafts are under `slck/deploy-notices/`, one per example; apply any reviewed edits to the renderer before enabling it.

The receipt deliberately overlaps the controller's existing plan/receipt fields: `notice_version: 1`, `deployment` (falls back to `source_branch`), `mode: dev|prod`, `status: success|failure|cancelled`, `stage: build|upload|verify|finish`, `sha` (full forty characters or null), `source_branch`, `repository` (`owner/name`), `host`, `verified` (boolean), `dirty` (boolean or null), `actor`, `actor_source: local|github`, `attempt`, `cloudflare_deployment`, `cloudflare_url`, and `run_url`. Missing revision, initiator, Cloudflare receipt or verification stays explicitly unrecorded. A build failure can be reported before any Cloudflare deployment exists. The receipt may contain other controller fields, but only the explicit display allowlist reaches Slack; no account identifiers, credential fields, arbitrary stderr or provider response bodies are rendered.

**Format (Ryan, November 14):** a notice is its sender name plus one line, the height of the avatar. The outcome is the sender name (`chat.postMessage` `username`, with `chat:write.customize`): `🚀 HF prod deployment succeeded`, `🧪 HF dev deployment succeeded`, `💥 HF dev deployment failed during upload`, `⏹️ … cancelled` (lead emoji since November 20; per environment since November 21, below). The line: `[hf] ([60b64bc31])` (branch and short commit, each linked), then warnings only where something is off (`⚠️ dirty`, `⚠️ tree state not recorded`, `⚠️ unverified` for a success without serving verification), `:gh: [actor]` (the GitHub profile; a local user is `:computer: `name``), ``attempt `df94aa1e` `` (the attempt id's first 8 characters, which receipt this is; Ryan, November 15), `:cf: [deployment id]` (the Pages deployment), `[site]`, `[logs]` (the Actions run). A clean tree and a passed verification are the norm and say nothing; the full attempt id stays in the receipt.

Manual `site/deploy` captures the source revision/tree state, installs its EXIT handler before building, and writes an attempt receipt under `tmp/` (`DEPLOY_NOTICE_RECEIPT` overrides the path). It records the actual build/upload/finish result and any deployment URL printed by Wrangler. The site slug comes from `STORE`, else the Pages project. A local username is labelled as such; it is not an authenticated assertion that a particular staff member deployed. Manual upload notices conservatively leave serving verification unrecorded; the existing entry-asset content-type checks do not establish exact build/data parity. The original deploy exit status is preserved even if receipt generation or notification delivery fails. Help, status and dry runs send nothing and write no notice receipt.

The controller should generate the same compact receipt from its trusted plan and actual job outcome, including a failure before `begin` or upload. Set `verified: true` only after its Cloudflare source/build/entry-asset checks succeed. Supply `GITHUB_ACTOR` as the actor and the workflow attempt identity. Run the notifier once in a separate final job, outside the Pages-upload credential step, with only its channel-scoped notification capability. A workflow retry is another labelled attempt; do not blindly rerun a send whose acceptance is unknown.

## Transport and review gate

Threading contract (Ryan, November 11; reds since November 13; per environment and quiet greens since November 21, below): notices are run-length threaded by color, greens and reds alike. Each deployment's consecutive notices of one color in one environment share one thread: the first notice after one of the other color (or with no notice of that deployment's and environment's in the channel's last 100 top-level messages) is a top-level post, and each later notice of that color joins its thread: a red replies, a green edits the thread's head (quiet greens). A failure and a cancellation are both red. A change of color ends the run; the next notice opens a new thread.

A webhook can't do this (it returns no message `ts` and can't read the channel), so the transport is the deployment's Slack bot through `thrds`'s `SlackClient` (`chat:write`, plus `channels:history`/`groups:history` to find the run; the HF Usage Bot has both). Before every post, `send` reads the channel's newest 100 top-level messages and takes the newest of this bot's notices for this deployment and environment (`run_head`), recognized by its sender name (`🧪 HF dev deployment succeeded`, `💥 HF dev deployment failed during upload`; any lead emoji; before November 14, the text's bold first line); if that notice has the same color, the notice joins its thread. The state lives in the channel itself, so manual and CI deploys continue one run without a store. Unfurls are off. Keep the token out of receipts, source, arguments and logs; no GCP credential, D1 token or Pages upload token is needed by the sender.

The sender uses a fifteen-second socket timeout and never retries an uncertain send (a `thrds` 429 retry is safe: Slack refused it). A failed history lookup posts nothing. Acceptance may be unknown after a timeout; the error stays explicit without printing the token or response body. Manual notification failures emit a warning and preserve the deployment's result. The CI notification job should expose delivery failure separately from the already-recorded release result.

Ryan approved the example copy with the threading contract above (November 11). To activate: give the sender the bot token and channel ID (`SLACK_DEPLOY_BOT_TOKEN` from the deployment's Slack bot secret, `SLACK_DEPLOY_CHANNEL`), wire the separate controller notification job, and enable the flag. Verify one real notice and independently read it back, checking project, environment, exact source, initiator provenance, links and threading. Do not describe notifications as live before that check.

**Every deployment (Ryan, 2026-11-18):** release notices go to each deployment's `#<d>-admin`, from `cloud`, not per-environment settings. The channel is `admin_channel` in `deploy/oa/sites.json` (the same channel as its `nominal` run threads); the controller's plan carries it and the notice step posts there whenever the environment holds `SLACK_DEPLOY_BOT_TOKEN` (the deployment's own Slack bot: hf's HF Usage Bot, gcs's gcsusage, …; it needs `chat:write`, `chat:write.customize` and `channels:history`), and skips with a notice when it doesn't. Adopting is one secret per environment, set by the deployment's owner: `gh secret set SLACK_DEPLOY_BOT_TOKEN -e <d>-dev|-prod`. The old `DEPLOY_NOTIFICATIONS_ENABLED` / `SLACK_DEPLOY_CHANNEL` environment variables are unused (hf's can be deleted). A manual `site/deploy` still reads both from its environment.

## Per-environment threads and quiet greens (Ryan, 2026-11-21)

Requested by Ryan, 2026-11-21: Slack should notify only when something is wrong. Every green reply notified the thread's followers and left an unread, and prod and dev shared threads.

**Per environment.** A deployment's prod and dev notices each run-length thread by color on their own: a dev failure doesn't end prod's green thread, and the next dev green after it opens dev's own thread. The thread lookup matches the environment the sender name (or a legacy notice's bold headline) names. `deploy_threads` on the deployment's entry in `deploy/oa/sites.json` picks it: `env` (the default) or `shared` (one run across both environments, as before).

**Lead emoji per environment.** A prod success leads 🚀, a dev success 🧪; a failure is 💥 and a cancellation ⏹️ in both (red needs no second glyph to stand out, and the sender name names the environment). `deploy_emoji` keeps today's flat form (`{"success": "✅"}`, both environments) and adds a per-environment one (`{"dev": {"success": "🧫"}, "prod": {…}}`); both may be given, and the environment's own entry wins (`site_emoji`). `record` resolves it for the notice's environment into the receipt's flat `emoji`.

**Quiet greens.** `deploy_quiet` (default `true`): a green notice whose thread is green posts nothing. It edits the thread's head instead (`folded`, `chat.update`, which notifies nobody and leaves no unread): the head keeps its own line (the first notice's) and gains one line, `N successful <env> deploys in a row · latest <YYYY-MM-DD HH:MM> UTC: <the newest notice's line>` (shared threads: `N successful deploys in a row · latest <time> (<env>): …`), which each later fold replaces. The design is stateless like the rest of the sender: N is read back from the head's last line (a head with no fold line counts itself and its `reply_count`, so a thread from before quiet greens carries on its count), and the time is the send's. The head's sender name is fixed when posted (`chat.update` ignores `username`), so the thread stays findable. A red still posts (a new top-level thread when the color changes, a reply in a red thread), and a green after a red, or with no notice in the window, still opens a new top-level thread: recovery is news. With `deploy_quiet: false`, a green joining a green thread replies, as before.

Choices made in implementation: a success with warnings (`⚠️ dirty`, `⚠️ unverified`, `⚠️ tree state not recorded`) is still green and folds quietly; its warnings show in the fold line. Two sends folding into one head at the same moment can lose one count (each reads N, then writes N + 1); the newest line is still one of theirs. A fold whose edit fails is reported as an unknown acceptance and not retried, like a post.

## Cloudflare-native comparison

[Cloudflare Pages project alerts] support deployment started/succeeded/failed events filtered by project and environment. They can cover deployment paths outside our helper/controller, including dashboard operations. [Cloudflare webhook destinations] can deliver alerts to Slack. Native alerts use provider-controlled copy and need separate account notification configuration; the local `CLOUDFLARE_API_TOKEN` returned HTTP 403 when reading alert policies, so existing native policy coverage remains unverified.

The reviewed receipt-based path additionally covers build failures before Cloudflare receives an upload and distinguishes upload completion from serving verification. Its initial scope is the shared manual helper and the release controller, across all configured sites and both environments. Direct Wrangler/dashboard operations bypass that integration. If those paths must be included, choose native event delivery or a shared event reconciler explicitly; do not enable native and helper/CI terminal messages for the same event and call the duplicates coverage. No native alert policy was changed during this work.
