- Render from recorded terminal top-level scan runs, scoped by deployment and store. Preserve failures, warnings/phase issues, no-ops, running and unknown results in the source sequence; never filter them out before computing a streak. Only a succeeded run with no unresolved phase issues counts as clean. Label scheduled, manual and unknown triggers distinctly; a manual success is not evidence that the daily cron ran. Unknown or truncated coverage must not be presented as an exact all-history streak.
- The parent states the latest completed scan and time, current consecutive clean-run count, scheduled/manual mix for its displayed window, and a scan-history link. Replies include the run time, trigger, result, duration and exact run link; include probe/phase evidence only when recorded. - Maintain one nominal thread across successes. Keep existing top-level failure/warning alerts. A failure closes the nominal streak; the next clean result starts a recovery thread in the channel so recovery is visible. Reply without broadcast during ordinary success. Keep thread identity separately from channel position: unrelated browser-activity posts must not cause a new scan-health parent.
- Use `thrds` for send/edit. Persist parent/reply IDs under a deployment/store namespace. Re-running or recovering after an interrupted backfill must not duplicate replies, change foreign replies or rewrite failure history. Serialize concurrent writers or use an atomic claim; do not rely on an unguarded read/update/write of a remote JSON file. Reporting failures must be observable and must not change the scan's recorded result.
- Report after the authoritative run record is finalized, including nonfatal phase outcomes. Do not call a run clean from a post step that runs before the head's final status. Do not enable automatic posting until the user has reviewed the parent/reply template. Preserve `DT_ALERTS=stderr` and scratch/off suppression. Posting, editing channel description/topic, and pinning remain subject to the user's Slack review requirement.

Local directories are supported for tests; remote state currently requires GCS for its generation preconditions. Site, store, kind and channel are part of the state namespace. State keeps at most ten recent run-to-reply IDs, one parent, and at most one pending send intent. Owned message metadata recovers an accepted send whose response or subsequent state write was lost. Foreign replies are never edited or deleted.

Unsupervised jobs report only after their final record is written; supervised jobs defer until the supervisor has applied any signal/termination override. `DT_RECORD=off`, dry runs and `DT_ALERTS=stderr|off|0` suppress the reporter. Notification failures are logged/redacted without changing the job exit result. A run with any historical phase issue is conservatively a streak boundary even if a later check recovers it. Missing phase evidence is refused; a vanished previously recorded history boundary refuses an update rather than falsely declaring a recovery or restarting the streak.
