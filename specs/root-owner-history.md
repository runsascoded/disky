# Compact root owner history

Status: `OWNER_HISTORY_BATCH` now means a bounded window per request (below), off on dev and production until measured on dev. The whole-history batch prototype this spec began with stays rejected. Compact artifacts remain the way to make a whole series one read; they need the user's design approval and are not built.

## A window of scans per request

`/api/series?o=…` (2026-11): 14 user-visible 503s at about 32 s of Worker CPU each, on many paths. Profiled in Node against gcs's live stores (`site/bench/view-mem.ts`, one cold process per request): about 85% of the CPU is decoding row groups, not the ledger fold. The cause is the store's layout: a path's closed versions are spread over the dyadic time blocks (`specs/interval-store.md` §2.4), at most 2S of them, each sorted on its own. A point at one scan touches about log2 S of them, a whole history all of them: 204 distinct groups (240 decodes) at S = 124 for a path with a few rows in each, about 0.13 s of CPU a group on the edge. A single version read doesn't change that (the same groups, and the 60-group cap below refuses it), and the cost grows with S.

Cost per request now, aligned window of K = `SERIES_CHUNK` = 16 scans: the 2K blocks inside it, log2(S/K) above it, the open segment, per tier, at most two groups each: G ≤ 2·(2K + log2(S/K) + 1 + 2·tiers), independent of S. Measured: 32–34 groups, a seventh of the whole request's CPU, at root and at a drilled path alike. The reader decodes each group once, the columns a total needs only (30% less CPU and memory than per-scan points over the same window). Past its group cap it falls back to the per-scan reads of the same K scans, also bounded. The fold stays O(K · assignments).

The client reads the newest window, then the others newest first, two at a time (`fillSeriesWindows`), drawing as they come. A window's cache key names only its scans, so a new scan leaves the older windows cached; a ledger change still makes them cold, each still bounded. Parity: every point of the concatenated windows equalled the whole series on the live stores at root and at a drilled path (all 124 scans); fixtures compare pools at every depth with assignments, base and runs. A lens's history reader stays root only (below the root a covering assignment wants the path's total, which its rows don't hold); lens and class series are windowed over per-scan reads. A share card reads the newest window only.

To turn on: `OWNER_HISTORY_BATCH = "1"` in `[env.preview.vars]`, compare `dt-cloud probe` full bodies with prod, check `cpuTime` in the analytics, then prod.

## The first prototype

The existing interval slice sorts carry exact owner bytes and object counts over multiple dates. The personal-owner root history fast path uses the user-first sort, reads the selected user's needed depth-1 versions once, combines base/run close records by minimum `vt`, filters each held date, then invokes the existing per-date live-assignment fold. It does not use stale snapshot ownership or estimate objects from bytes. Uncovered dates, missing slice sorts, bounded-read refusals, or unreadable history use the canonical per-scan reader. Broad owner pools, drilled, multi-path, class, and text-query histories retain their existing readers.

Limits: 60 selected row groups and 100,000 retained root versions. The raw depth predicate avoids shaping unrelated rows, and decoded-group storage remains in the existing bounded cache. The response cache keys distinguish disabled and enabled reader revisions, so comparison does not reuse a prior fallback response. Server-Timing reports history time, the count of covered points, and any explicit fallback reason. All-owner batching is rejected: the first 60-group limit refused the real fleet's 127-group root history; increasing it to 160 caused Cloudflare 1102 errors on dev and was not promoted. The user-first plan restores the smaller cap and leaves broad pools on the canonical reader.

Fixtures cover per-user and owner pools, ancestor repainting, releases, exact-object assignments, base/run close records, and uncovered dates. Live complete-JSON comparisons passed all four scoped histories when the canonical fallback answered. The user-first plan still selected 132 groups for the first tested owner and 86 for the other (cap 60); it added planning time then fell back. It did not demonstrate a speedup, and the flag is disabled. The full site suite passes 1,907 tests with one skipped; source types/build pass.

The compact artifact must retain per-scan owner bytes and object counts plus coverage/generation identity. Current live assignment overrides must still be applied at read time. Pin publication to immutable source generation and complete coverage; missing artifacts fall back, not zero. Compare complete historical responses to the canonical reader and measure response-cache misses, including concurrent page loads, before enabling it. Broad pool reads must remain bounded too. No additional scan, historical rebuild, new artifact publication, migration, or daily image change was performed for this prototype.

`dt-cloud probe -R /api/... -a <baseline URL>` compares complete JSON bodies (including every historical point), not just net/root totals, and records timing/cache headers for both deployments without storing successful private response bodies. Both deployments use the supplied viewer credential; choose only intended trusted origins. `-S` makes requests serial; default is concurrent. Response-cache misses do not imply cold lower-level caches.

## Correctness gate: compact totals alone are insufficient

The canonical root read has two independently costly inputs: snapshot-attributed depth-1 owner rows and `ownerAssignments(date)`. On a cold ledger head, the latter calls `ownerTotals`, which prices every live assignment prefix against that scan. Replacing only the first input does not remove the second bottleneck. The existing snapshot `meta.json.users` also carries bytes but not exact per-user object counts, so it is not a valid substitute.

Arbitrary current assignment/release/object overrides require each affected historical prefix's total bytes/objects and its original per-owner byte/object vectors. A single root owner vector cannot reconstruct those corrections. Preserve zero-byte objects independently of byte totals. Do not infer objects from bytes or use the existing `owner_totals.users` byte/class-only shape as an exact object series.

Two compact layers are needed: an immutable, source-generation-pinned `(scan, bucket, owner/null, bytes, objects)` root basis, and complete live-ledger corrections. Corrections may either retain the historical per-prefix vectors needed by the existing fold or materialize the **final** root vectors at a specified ledger head. For the initial pilot, a head-pinned final vector is the smaller implementation: publication pins the exact ledger input; serving compares the current head and refuses a mismatch. This applies live assignments by strict head validation, not by presenting stale snapshot ownership as live. Re-read the ledger head before marking the result complete; publication must not silently relabel a result computed from an earlier head.

A future background correction builder is a separate requirement: assignments cannot leave old-head results visible while it runs. Until current-head coverage is complete, the canonical reader remains the fallback, with its existing latency/failure risk explicitly acknowledged. A warm assignment-cache benchmark is not proof that cold requests or newly changed ownership are fast.

## Smallest bounded pilot and authority boundary

1. Local synthetic fixtures first: complete byte/object series bodies across four scans, unassigned and newly assigned users, ancestor repainting, releases, exact objects, zero-byte objects, missing paths, missing scan coverage and ledger-head changes. This needs no cloud mutation or production scan.
2. With explicit approval, materialize locally from **four selected existing published scans** only. Cap source transfers at **128 MiB total**, planned before downloads; refuse over-budget plans rather than expanding the scope or sampling. Reuse only already-computed current-head assignment pricing. If that pricing is absent/stale, report the refusal—do not launch historical repricing, a scan, a large VM or a daily image rebuild. Record source generations, ledger head, read bytes/groups, compact payload size and build time in private runtime evidence, not public data-bearing specs.
3. Compare every selected point and complete bounded response to the canonical fold. No site flag or production artifact is enabled by this local pilot. A dev-only immutable artifact publication is a subsequent explicit approval, under a fresh prefix with a complete manifest and no overwrite of published sources.
4. Production acceptance requires complete coverage of the served scan set and current ledger head, bounded all-owner reads, complete historical-body parity and response-cache-miss timings under concurrent page loads, including a cold correction state and a new ledger head. Drills, text queries, classes and multi-path series retain their current readers. Do not claim that a four-scan pilot repairs the full historical endpoint.
