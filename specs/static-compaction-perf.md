# Static compaction and carry merges: why they take 12+ h and 361 GiB, and the levers

Status: analysis (2026-10-23) plus two levers built in `cc153391` (see "Built"). Remote tests have **not** run yet (the test node needed an AWS SSO login). Target: a compaction under 1 h on one VM, and a working set that doesn't scale with the corpus (≤ 64–128 GiB RSS).

## Root cause 1: the rows are the drill, not a blow-up; the fold makes ~6 passes and a global sort over them

The "~95 B intermediate rows from a few B" reading is not what happens. The drill **is** ~55 B rows: one root row per (heavy literal `q`, root path, owner slice, version), and each changed path is indexed under many literals. 45,109 canonical long literals × ~0.88 M roots each ≈ 39.5 B, plus 15.3 B short-literal roots; the base's `drill/` (279 GiB) holds the same order of rows. The three counts are three passes over the same data:

- `long-roots` (`static_compact.py:195-215`) combines each member-tuple's rows across tiers (base read per chunk by its classes' `q` span, the runs' rows from the spill) and digests them: 40.06 B rows (tuples, `tid`; 1.4% more than the canonical set, because 47,595 tuples merge back to 45,109 classes by digest).
- `canonical-roots` (`static_compact.py:231-239`) reads all of them back, renames `tid` → canonical `q`, adds `depth`, and re-partitions from tuple order to `q`-range order (`spill_roots`): 39.5 B rows written a second time. It exists only because the output must be in `q` order and the chunks are in tuple (`c0`) order.
- `short-roots` (`static_compact.py:253-267`): the short literals' 15.3 B rows, combined and spilled by `q` range.

Then `finish_drill` (`static_local.py`, before `cc153391`): `measure_ranges` reads every range back for the measurement and rollups (pass 4), and `build_drill` → `write_kind` with no `chunks` ran `_cut` (`GROUP BY q` over a view of every spill, pass 5) and, per output file, `SELECT … FROM <view of every spill> WHERE q range ORDER BY q, path, usr, vf` (pass 6, a DuckDB external sort of 55 B rows with ~1 TB of temp). That sort is the 12 h+ tail. `ab97c805` streamed `merge_tiers`' write but not this one.

The steps also pay twice for `q`-range assignment: `spill_roots`, `merge_tiers`' read and `short-map` used `rows ASOF JOIN bounds ON q >= lo`. DuckDB's ASOF join has no equality key here, so it sorts its whole left side in one partition (`asof_loop_join_threshold` = 64 only covers tiny left sides). Every spill was a sort of its input. This is the likely main cost of the carry's 60 + 17 min `read/*`: 2 B rows at ~0.5 M rows/s, far below parquet decode or gcsfuse throughput. It is also paid per chunk in `canonical-roots` and `short-roots`.

`drill/fold/plan` (`static_compact.py:172-180`) is a full pass too, 1 h. `tc{i}` counts every tier's long roots per `q` (the base's 40 B rows from the GCS mount) only to size chunks. An estimate would do, because chunking never changes bytes.

## Root cause 2: RSS sits at the container limit by design, and above `-M` from allocations DuckDB doesn't track

- `-M 270GB` lets DuckDB's buffer pool grow to 270 GB, and it does. DuckDB 1.5's `enable_external_file_cache` (default on) keeps the parquet bytes it reads in that pool, and materialized intermediates (`tc*`, `mt`, `tup`, `ct`, the `lrup`/`srup` rollup tables) sit in it until evicted. The plan step's 174 GiB is a read-only scan filling the cache. RSS ≈ the limit says nothing about need. Every fold step is already chunk-bounded (~8 M rows a chunk), so the need is a few GiB per thread.
- RSS went ~90 GiB past the 270 GB cap. `rss_peak_gb` is `ru_maxrss`, a monotone peak, so the jump is from `runs-spill` (174 → 272) and `long-roots` (→ 356). `runs-spill` is a `COPY … PARTITION_BY (ch)` over **4,858** partitions. DuckDB keeps per-thread, per-partition buffers (`partitioned_write_flush_threshold` 524,288 rows) and closes and reopens files past `partitioned_write_max_open_files` (100), and that memory is not all under `memory_limit`. Add jemalloc retention and the Arrow results pulled into Python. Pyarrow itself is not the term: the only large Arrow objects are `aliases` (94 K rows) and the writers' row groups.
- Fix: size `-M` to the working set (e.g. `-M 48GB` on this VM) and partition spills into tens or hundreds of files, not thousands. The `PARTITION_BY` fan-out is lever 4. With the global sort gone (`cc153391`) nothing in the fold needs more than a chunk plus the rollup tables.

## Floor

Input: the base drill, 279 GiB (~55 B rows), plus the runs' drills (tens of GiB); output about the same. The intrinsic work is one decode of the inputs, a per-`q` combine (min `vt` per key: a merge of sorted inputs, not a hash aggregate), a per-`q` measurement and rollup, and one encode plus index. On 48 cores, figure ~1 GB/s of compressed parquet per pass for DuckDB decode, plus parallel zstd encode:

- read + combine: ~5–10 min
- measure + rollup (per-`q`, chunked, already parallel in DuckDB): ~10–20 min
- write: 55 B rows. The serial writer (`write_sorted`, one Python callback per 8,192-row group, ~6.7 M groups) is ~1.5–3 h single-threaded, ~10 min over 16 processes.

Drill floor ≈ 30–45 min. The non-drill parts (intervals, shards, catalog: 65 min today) run one range at a time (`fold`'s `jobs` is unused) and parallelize the same way, to ~10 min. **< 1 h end to end is reachable, but not with the current pass structure.**

## Levers, ranked

1. **Stream the base drill's write.** Built in `cc153391`. `measure_ranges` writes each `q` range's roots sorted (it already holds them in a table for the measurement) and deletes its spill; `build_drill(sorted_roots=…)` hands those files to `write_kind`'s `chunks`, as `ab97c805` did for `merge_tiers`. This removes pass 5 and pass 6 (the 55 B-row external sort and its ~1 TB temp): an estimated several hours (the L3 carry spent 69 of 185 min in the same sort at 2 B rows). Work disk peaks at the spills *or* the sorted ranges (~0.5 TB), not both plus the sort temp. It also covers the one-machine `static-names build` (shared `finish_drill`).
2. **Assign `q` ranges by a hash join, not a per-row ASOF.** Built in `cc153391`. `static_roots.ranged`: the ASOF join runs over the distinct `q`s only (≤ ~100 K; `merge_tiers` uses `cmap`'s merged canonicals), and rows take their range by an equi-join. Same rows, same ranges. Estimate: the carry's `read/*` from 77 min to I/O-bound (~5–10 min for 19.6 GB). Smaller per-chunk wins in `canonical-roots`, `short-roots` and `short-map`.
3. **Write files in parallel.** Built (see "Built (the tail)"). `write_kind`'s cuts are known before any file is written (`_cut_counts`), and each file and its index rows depend only on its own range. Run them over a process pool (each process opens its chunk files by range), then concatenate the index tables in file order. The bytes are unchanged by construction. Estimate: the write from hours (serial, ~5–10 M rows/s) to ~10 min. After 1 and 2, this is likely the largest remaining term, both here and in `merge_tiers` (the carry's 51 + 18 min write).
4. **One pass for the long roots, no `canonical-roots`.** Not built. Order tuples by their least member, not by the base's class. The kept tuple of each merged class is the one holding the class's least member, and its canonical `q` is that tuple's least member, so chunks of consecutive tuples produce `q`-disjoint, in-order output. `long-roots` can then write each chunk's kept tuples renamed and sorted, measure them in the same table, and skip the second pass and the spill (−1.5 h, −0.5 TB). The catch: a chunk's base classes then no longer span a narrow `q` range, so base reads by `c0` span get wider. Spill the base once by chunk, as the runs are (one sequential read of 279 GiB, instead of `q_spans` reads per chunk), and use few partitions (lever 5). Tuples merging back by digest (47,595 → 45,109) still need the digests before any write: keep the per-chunk `ct` files and choose the kept `tid`s after digesting, as now. Only the rename and sort move into a chunk-local second step that reads `ct`, not a global re-partition.
5. **Fewer partitions in spills; plan from the index.** Built (see "Built (lever 5)"). `runs-spill` partitions by chunk (4,858). Partition by ~64–256 super-chunks instead and filter by `ch` on read (row-group pruning on the sorted `ch`). This bounds open files and the untracked partition buffers that pushed RSS past `-M`. The plan's `tc{i}` counts can come from each tier's `long-roots-index.parquet` (per 8,192-row group: `q` first and last, rows). Approximate counts are enough because chunk sizes never change bytes. −1 h of plan and the 174 GiB cache fill. The same applies to `merge_tiers`' `plan` count pass.
6. **Size `-M` to the working set and turn off the external file cache for these jobs.** A config change: `-M 48GB` (or a fraction of RAM, chunk-bounded), `SET enable_external_file_cache=false` in the build's connections. RSS then tracks the chunk, not the limit. Do this once 1–5 have removed the unchunked steps; before `cc153391`, the global sort needed the large limit to avoid spilling 1 TB.
7. **Parallelize the light parts.** Not built. `fold_range` per key range and `fold_catalog`'s census per shard over `sn.each` (`jobs`): 65 → ~10–15 min.

Estimated end state (1–7): read and combine ~15 min, measure and rollup ~15 min, write ~10 min, light parts ~15 min, upload apart. About 1 h on n2-highmem-48 with `-M` ≤ 64 GB. With 1–2 alone, the 12 h+ run should fall to roughly the steps before measure (~9 h, unchanged) plus measure and a serial streamed write (~2–3 h), so 3 and 4 are needed to reach the target.

## The carry merge (`merge_tiers`)

The carry shares levers 2 (its `read/*`), 3 (its write) and 5 (its `plan` count pass). Its fold (14 + 5.5 min) is already chunked. Its write already streams (`ab97c805`). After 2 and 3, the L3 carry's ~185 min should be ~30 min, dominated by decode and encode.

## Built (the tail: measure, write, anchors, publish)

What follows the drill fold, made as parallel as the VM allows. Every pool spawns processes; each DuckDB task gets its own database (`static_names.ConPool`: the parent's `threads` and `memory_limit` split `jobs` + 1 ways, and the parent's limit is lowered to its share while the pool runs; if the parent can't shrink, it keeps its limit and the line is logged). Module constants a test patches are resolved in the parent and passed down: a spawned process sees only the modules' defaults.

- **Measure** (`static_local.measure_ranges`): `threads // MEASURE_THREADS` (4) `q` ranges at a time, each in its own process (12 on `-p 48`). Each range's measurement and rollups go to parquet first, then into `ldirs`/`lrup` (`sdirs`/`srup`) in range order. Their consumers sort them (`roots-measure/`, `write_kind`), so `jobs` never changes bytes. Before this, ~13 K ranges (55 B roots / `CHUNK_ROWS`) each ran a few dozen small statements, one range at a time, on one 48-thread database.
- **Write** (`static_drill.write_kind`): sorted-chunk files go out `write_jobs()` (every core) at a time in processes, instead of 8 threads behind one GIL (a writer runs Python per 8,192-row group, ~6.7 M groups). Each process gets only the chunks that overlap its range. `_sorted_chunks` counts 16 files at a time on cursors. A table-sorted kind (the base's rollups) writes `SORT_WRITERS` (4) files at a time, each from its own cursor's `ORDER BY` over its range. The carry's `merge_tiers` write gets the same pools.
- **Anchors** (`static_local.build_base_anchors`: the base's and a compaction's `names/` + `anchors/`): `static_anchors.build_tier_local(jobs=)` builds the `end` and `exact` rollups and the starts-with catalog one shard at a time, `threads // ANCHOR_THREADS` (4) shards in parallel, biggest first. A key, and a `^q` prefix (≥ 3 characters), lies in exactly one shard, as on the staged path, which already builds per shard. Each shard's cells are sorted to parquet, then streamed in shard order into the same single files (`write_rollup_parts`, `write_start_parts`). That replaces one DuckDB job over every suffix row (a hash aggregate over billions of keys). `write_names(jobs=)` plans the shards from each three-character prefix's rows (`name_plan`: `write_run_shards`' cut exactly), spills the rows once by shard (≤ 64 partitions), and writes each shard (sorted, plus its sidecar) in its own process. `shards.json` and `sidecar.parquet` come out as the stream writes them. Per-scan appends and carries keep the serial path (`jobs` 1).
- **Publish** (`blobstore.upload_new(tier=)`): in the store's publish order, consecutive keys of one tier go up `UPLOAD_WORKERS` (32) at a time, and all of them finish before the next key starts. A key of tier None goes up alone: every `meta.json`, `scans.json`, the manifests and `compaction.json` (always last). `static_local.publish_tier` / `interval_local.publish_tier` put every data file in tier 0, and the compactors pass them (`Compactor.publish_tier`). So data before its markers, markers in their order, and the pointers after the upload all hold as before. `compaction.json`'s md5s hash 16 files at a time. `r2_publish_gen` copies 32 objects at a time (`R2_WORKERS`). Its `last` files still go one at a time after the rest, then the check, then `successor.json`, then `CURRENT.json`. The R2 client's pool is 128 connections: botocore's default of 10 serialized 8 workers × their multipart threads.
- Not done: GCS composite or XML-multipart uploads. Those objects carry no MD5, and the R2 copy's skip test and its md5 stamp (`publish.should_copy`, `copy_one`) rely on the GCS md5. Parallelism is per file instead: the drill's files are ≤ 50 M rows, and 32 streams saturate the disk or NIC.
- Byte identity: `test_parallel_tail_is_the_serial_one` (`drill/`, `roots-measure/`, `names/`, `anchors/` at 4 processes per pool, `-c 1`, against the serial build), `test_parallel_names_are_the_streamed_ones` (`write_names` at 3 processes, shards cut at 1 and 7 rows), `test_writing_sorted_chunks_writes_the_same_bytes` (`write_kind` at 4 processes), and the compaction-is-the-rebuild tests. Order: `test_publish_steps`, `test_upload_new_puts_each_step_after_the_last` (no marker starts before every data file ahead of it has finished; 4 in flight), and `test_publish_order` for the interval store.
- Expected on n2-highmem-48 for a ~300 GiB generation (estimates, not yet measured live): measure + rollup ~30–60 min (CPU-bound, 12 ranges at once; it was hours serial); write ~5–10 min (48 processes, bound by reading ~280 GiB of sorted ranges and writing as much; plus ~2 min counting); anchors ~20–60 min, scaling with suffix rows / 50 M shards × ~1–3 min per shard ÷ 12, plus names ~10 min; md5 ~3 min (was ~10); GCS upload ~3–6 min (was ~35 min at one stream); R2 copy ~6–10 min, NIC-bound (was ~20–30 min at 8 workers on 10 connections).

## Built (lever 5)

- `static_roots.index_estimates(con, index_files, keys, into)`: per key, its rows estimated from `GROUP_INDEX_SCHEMA` indexes alone (each group's rows spread evenly over the keys in its `[q_min, q_max]`, the remainder to the first; exact for single-`q` groups). The compaction's `drill/fold/plan` (`tc{i}`: per tier, keys = its alias map's canonicals), its short-roots plan (keys = the short indexes' group bounds; the per-range file selection now uses the range bounds, not the counted literals) and `merge_tiers`' `merge/<kind>/plan` (per input, keys = `cmap`'s `ci`, summed per merged `c`) read the indexes instead of counting every row. `merge_tiers` also skips the `lit` scan for the long kind (only the short kind's `cmap` uses it).
- `static_roots.ChunkSpill`: a spill by chunk `ch` goes into at most `SPILL_PARTS` (64, under DuckDB's 100 open files) partitions of consecutive chunks; the reader, reaching a partition of several chunks, splits it by chunk (one more local pass over that partition, fan-out ≤ ⌈chunks / 64⌉) and drops it on moving on. Used by the compaction's `runs-spill` (4,858 partitions → 64) and `merge_tiers`' `read/*` (unchanged while a carry has ≤ 64 ranges). `fold_drill`'s chunk numbers are made dense first, so partitions are even.
- Byte identity: chunk sizes and partitions never change output. Pinned by `test_compacted_generation_is_the_rebuild` (new worlds `d`, `e`: `-c 3` with 2 and 1 partitions), `test_chunked_drill_merges_write_the_same_bytes` (new: `chunk_rows=2` at 1 and 2 partitions), `test_index_estimates_spread_each_group_over_its_keys`, `test_chunk_spill_reads_each_chunk_exactly` (1, 2, 3, 7, 64 partitions over 7 chunks).

## Built (fold parallelism, `-j`)

Measured on the 10-23 live compaction (n2-highmem-48, `-M 270GB -p 48`): the `[alive]` lines during `drill/fold/long-roots` showed 850–1,000% CPU of 4,800%. The 4,881 chunks ran one after another, and each chunk's query used about 9 cores.

- `fold_drill(jobs=)`: the long-roots chunks, the canonical-roots files, the short-literal ranges and the runs' spills run `jobs` at a time (`static_compact._pool` over `static_names.each`). Each item gets its own cursor of the one DuckDB database, with temp tables per cursor, and writes its own files. Cursors share the database's `threads` pool and `memory_limit`, so total DuckDB memory stays at the profile's `-M`, not `-M × jobs`. Long roots' digests come back per chunk and go into `tdig` once. The runs' spill is read a whole partition batch at a time (`ChunkSpill.prepare` / `release`, ≥ 4 × jobs chunks per batch). Concurrent spill writes split `partitioned_write_flush_threshold` (a per-connection setting) so their untracked buffers add up to one write's.
- `SET enable_external_file_cache=false` on the fold's connection.
- Jobs: `static_merge compact -j` comes from the profile's `fold_jobs` (`STATIC_NAMES_FOLD_JOBS`; 0, the default, means one chunk per 6 vCPUs, so 8 on n2-highmem-48). `static_compact compact -j` does the same on one machine.
- The checkpoint steps, tables and files are unchanged. A checkpoint is keyed by `code_version()`, a hash of every `.py` file in the package, so a run started on an older image restarts its fold from the start rather than resuming.
- Byte identity: worlds `f` (`-c 3 -j 4`), `h` (1 spill partition, split on reading, `-j 4`) and `i` (two level-0 runs, `-j 4`) equal the rebuild. The resume test stops at each step at `-j` 1 and 4 and resumes at the other value.
- `static_merge compact-probe`: the compaction's fold of a generation read in place from the mount, with no lease, checkpoint, upload or pruning. It writes a report (per-part seconds and peaks, plus every output file's size and md5) to compare with the published `compaction.json`.

## Built (lever 7)

Measured before it (live n2-highmem-48 compaction, 2026-10-23): intervals 1,139 s (RSS 25 GiB), shards 1,281 s (`merge_shards` 978 s at 48 processes + its checkpoint save 296 s), catalog 1,145 s (RSS 64 GiB); ~60 min before the drill.

- `static_compact.fold_ranges`: the key ranges fold `jobs` at a time (`static_names.each`: cursors of the fold's one DuckDB database, so `-p` and `-M` are shared, not split by hand); `fold_range`'s table is named for its range.
- `fold_catalog`: the census runs `jobs` shards at a time on the same cursors (`static_catalog.census(tag=…)` names its working tables per shard). `cut_members` is unchanged (one small read of the census files).
- `fold_gen`: `merge_catalogs` (reads only the tiers' catalogs) starts at the beginning in a background thread, beside the intervals and shards; the catalog part waits on it after its census. It isn't started when the catalog part is restored from a checkpoint.
- `fold_gen`'s part saves (`Checkpoint.save_files`) run in the background, beside the next part: one at a time, in part order (a part's save is waited on before the next part's is queued), and the drill, whose own steps save synchronously, starts only once the saves before it ended. Step names, files and order are unchanged; a failed save surfaces when the next part ends (no later step is saved). `fold_gen` waits on all background work as it returns or fails.
- `jobs`: `static_merge compact -j` (the shared `compact_options`), `static-names compact -j`; the static chain's compaction job passes one per 4 vCPUs (`static_runner.compact_jobs_args`: 12 on n2-highmem-48).
- What stays serial: the shards need every range's histogram (`plan_shards` over all of `chist/`), the census needs the shards, the drill needs the members, so intervals → shards → census → drill is a chain. `merge_shards` was already one process per shard. `merge_catalogs` is one streaming k-way merge into one file of `CELL_RG` groups (cutting it by key range would need group-aligned bounds); it is overlapped instead.
- Byte identity: every range's and shard's files depend only on their own rows. Pinned by `test_compacted_generation_is_the_rebuild` (new world `f`: C at `-j 4`) and `test_a_fold_stopped_after_a_saved_step_resumes_there_to_the_same_bytes` (now at jobs 1 and 4, stopping after each part's save too).
- Expected on n2-highmem-48: intervals ~2–4 min (the 1,139 s is per-range serial DuckDB + one pyarrow writer at a time; 12 at once), shards ~16 min (`merge_shards` unchanged; the 296 s save now overlaps the catalog), catalog ~2–4 min (the census 12 at once; the merge hidden behind intervals + shards if it is under ~20 min). ~60 → ~22 min, dominated by `merge_shards`. Not yet measured on a live run.

## Built (staging the roots)

Measured before it (`compact-probe` of 2026-10-08c at `-j 8`, n2-highmem-48, 2026-10-24): during `drill/fold/long-roots` CPU sat at ~40% while network-in held a steady ~550 MB/s, ~1 TB read in ~30 min for a ~280 GiB base drill: each base byte through gcsfuse ~3–4×, throughput-capped. Not the chunk bounds: chunks run in base-class order, each reads its `q` span's row groups (8,192 rows) and the footers are cached per cursor, so groups cut by two chunks cost ≤ 2 × 8,192 rows of ~4 M per chunk (< 0.5%). The excess is the mount's ranged reads (concurrent chunks defeat its sequential read-ahead), so aligning chunks to row groups wouldn't recover it.

- `static_compact.stage_roots`: every tier's `{long,short}/roots/*.parquet` copied to `<work>/stage/` by `blobstore.stage_files`. From `gs://`: over the GCS JSON API (not the mount), in `STAGE_WORKERS` (32) spawned processes, each file cut into `STAGE_SLICE` (64 MiB) ranged GETs written in place into a preallocated `.part` (`STAGE_TIMEOUT_S` 600 s read timeout, client retries up to `STAGE_DEADLINE_S` 3,600 s, `STAGE_TRIES` 4 attempts per slice), then the whole file's crc32c (`google_crc32c`'s C path, in a worker) checked against the listing's, and renamed. Other roots (a local dir, `r2://`) copy through `Store.get` on threads. A progress line every 30 s: files, GiB, MB/s.
- Probe 4 (2026-10-24, the first version: 64 threads downloading whole files inside the fold's process) staged at ~24 MB/s and then failed the fold on an `IncompleteRead` past the client's 120 s retry deadline. `google_crc32c.implementation` is `c` (the lock has its cp312–cp315 manylinux wheels; the image is `python:3.12-slim`), so not a pure-Python crc: the likely cause is the GIL. Each 8 KiB read handed the GIL back and forth with the intervals' and shards' Python writers at ~3,600% CPU. Hence processes, slices and long deadlines.
- A cache, never a failure: a file whose copy still fails after its retries (or whose size or crc32c doesn't match) is logged (`… not staged (…); read in place`), left out of the map, and read in place; anything that breaks the copy as a whole (credentials, the pool) logs `stage: failed (…)` and the fold reads every root in place. The summary's `staged.failed` lists the files left out.
- Started by `fold_gen` in the background beside the intervals (the inputs are known at the start), so it overlaps the light parts; `fold_drill` waits on it before its plan. The long roots' copies are deleted after `long-roots`, the short ones' after `short-roots`. Not output and never checkpointed: a resumed fold stages what its remaining steps read (none past `spilled`, only the short roots past `long-roots`).
- `-s auto` (default): staged only when the generation isn't on the work disk already (a mirror, an `r2` read) and the work disk's free bytes cover the roots × (1 + `STAGE_HEADROOM` = 4: the fold's own peak beside them, 1,085 GiB over 279 GiB in 10-08c); otherwise read in place, with the reason logged. `on` stages regardless, `off` never. The decision and the copy's line are in the fold's summary (`staged`, `stage_log`).
- Wiring: `Compactor.source` makes `compact_store` hand the fold `source=store.uri(<prefix>/<gen>)`; `static-names compact -s`; `static_merge compact-probe -b BUCKET -s` (default `$DATA_BUCKET`; without one it copies from the mount).
- Byte identity: world J (`-s on`, `-j 4`) equals the rebuild; `test_compact_probe_folds_read_only_to_the_published_bytes` at `-s off|on|auto` (auto: no room → read in place) and with a copy error injected for one file, then for the whole copy; `test_stage_roots_modes`; the resume test reruns with `stage="on"`.
- Expected: staging ~300 GiB at 3–4 GB/s is ~1.5–2 min if the work disk writes that fast (local SSD write bandwidth scales with the device count; a few devices may cap it under 1 GB/s, ~5 min), hidden behind the intervals/shards/catalog. `long-roots` then reads local NVMe and should go CPU-bound: ~30 → ~12 min at 40% → ~100% CPU. `short-roots` gains likewise where it read the mount; `canonical-roots` reads only local `troots/` and is unchanged. Not yet measured live.
