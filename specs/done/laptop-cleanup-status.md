# Laptop cleanup availability and run reporting

The `/staged` console distinguishes the laptop cleanup agent's D1 check-in from the separate file-preview tunnel. An admin-only, uncached `GET /api/executor-status` returns `executor`, `ready`, `last_seen`, `checked_at` and `stale_after`; readiness and dispatch use the same 180-second threshold. The console polls every 30 seconds, offers a manual check, renders timestamps in the viewer's timezone and pauses dispatch controls when the agent is known to be disconnected. A failed status check is unknown, rather than a healthy cached result.

An offline refusal has code `cleanup_agent_offline` and explicitly says the request was not submitted and the items remain staged. Other network/server failures have an uncertain outcome: the console directs the user to check Runs before retrying. Neither reconnecting nor checking status retries a dispatch.

Each laptop request saves its immutable selected URI set in `deletion_runs.selected_items_json`, validated against the staged item kinds before dispatch. The drainer uses that snapshot even if the plan changes; an empty snapshot never falls back to the whole plan. Previously the laptop executor ignored `req.items`, and the worker reread the whole live plan. Once the schema supports snapshots, a request with no snapshot is refused with a recorded issue and no paths touched. This also protects the rollout window from an older site writing a request; no pre-snapshot requests were pending during the investigation. The old schema retains its legacy execution path.

The agent writes `executor_started_ts` before sizing or moving paths and writes `execution_errors_json` with its final totals. A failed path records zero successful bytes and objects in its band, so the prefix history cannot label a failed move as a successful deletion. The console distinguishes waiting for agent, running and completed with issues, exposes per-path errors and labels real laptop outcomes as moved to Trash. Older records lack per-path error reporting; their expanded detail says so. Moving to Trash does not reclaim space until the seven-day hold expires or Trash is explicitly emptied. The local executor acts on the current contents of checked paths; the cloud executors' scan-version preservation claim does not apply to this rename-based executor.

D1 HTTP requests have a 30-second socket timeout, allowing the existing transient-error retry loop to recover from network stalls. The original report proved a stale heartbeat (about 12½ hours), not the exact cause of that interval: the older agent logs have no timestamps. The post-restart user request `laptop-real-20261110t123148z` finished, recording 424,284,160 bytes and 367 objects moved to Trash; its local log also reported one already-missing path. No additional live dispatch was used for this fix.

Deployment order: add the nullable columns `selected_items_json TEXT`, `executor_started_ts INTEGER` and `execution_errors_json TEXT` to `deletion_runs`, restart the drainer so schema detection and the new code are loaded, verify a fresh check-in, then publish the site. Both dev and production use `disk-tree-m3-db`; its recipe was applied on November 10, 2026 and removed after the canonical schema matched live D1. Other laptop deployments need the same columns and worker/site ordering. Cloud executors require no behavior change.

Regression coverage uses SQLite D1 doubles, injected deletion functions and intercepted browser API requests. It covers heartbeat boundaries, auth and no-cache status responses, exact selected rows, plan edits after submission, an empty saved selection, per-path errors, queued/start/completion states, offline recovery, unknown status and narrow-screen rendering. Full Python and Vitest suites run on GitHub Actions; focused browser checks run with one worker. No verification invokes a real deletion.
