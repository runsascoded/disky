## Failure grouping (`nominal.group`, 2026-11-16)

Requested by Ryan, 2026-11-16: failing runs repeat more often than they differ, so a run of failures should share a thread the way a run of clean runs does, and anyone can reply under one failure to dig into it. A deployment picks how its runs group into threads with `nominal.group`:

- `clean` (the default; what HF and every earlier adopter run): only clean runs thread. A failure closes the thread ("clean-run sequence ended") and posts its own top-level alert, and the next clean run opens a new thread. Every byte this mode posted before is unchanged, except that a one-run streak now reads "1 consecutive clean run" / "Latest 1 run".
- `color`: consecutive runs of one color share a thread, as deploy notices do (`specs/deploy-notifications.md`). A failure thread's parent is "❌ **<title>: N consecutive failed runs**": since when, after which run (the last clean one), and the newest failure's reason. Each reply is "❌ <trigger> [<time>](<record>) · <duration> · <reason>". A change of color edits the old parent ("failure sequence ended" / "clean-run sequence ended", naming the run that ended it) and opens the next thread.
- `signature`: as `color`, but a failure thread holds only runs that failed the same way (`nominal.signature`): the phase a failed run failed in, or the set of phases a partial run's issues name. Error text is left out of the signature, since it carries times, ids and sizes that differ between runs failing the same way. A different failure closes the thread and opens its own; the parent says how ("… failed runs in interval-store", "… with phase issues").

A reason is the failed phase and the recorded (already redacted) error, on one line, clipped to 160 characters, with `<`, `>` and backticks replaced so an error can't become a link, mention or code span.

Under `color` and `signature` the failure thread is the failure's report: a top-level run's `fail` alerts are deferred (`nominal.defers_failures`, kept in the job's state file) and posted top-level by the finalizer only if the run did not become a reply in a failure thread (the report failed, was suppressed, or the thread didn't take the run). So the first failure of a run of them is the one top-level post, its thread's parent, and a repeat is a reply. `warn` alerts, child runs and other kinds/stores post at once, as before.

## Running replies (2026-11-17)

Requested by Ryan, 2026-11-17: a run should show in its thread while it runs, not only once it ends. `scan-run start`, after recording the run, reports to the thread (`nominal.report_start`): in the open thread, a live run (recorded running, or not yet finalized) gets a reply "⏳ <trigger> [<start time>](<record>) · running", and the head gains "Running now: <its start time, linked>". The thread's grouping is still decided by finished runs only, so a live run never counts toward a streak.

When the run ends, the next report (its finish, or any later run's) edits that reply in place:

- It ended in the thread it was posted in: the reply becomes the run's usual line (✅ or ❌), with no second reply.
- It ended elsewhere (option A, Ryan's pick): under `clean` grouping a failure closes the thread as before, and the ⏳ reply becomes the ❌ line followed by "· [alert](<permalink>)", the run's top-level `fail` alert when it went to this channel (the bot's own top-level post linking the run's record since it started; no link when there is none). Under `color` / `signature` the line links the thread that took the run instead ("· [thread](<permalink>)").

The ⏳ reply's message and thread are kept in the state file's `running` map (cleared as runs end); its send goes through the same persisted intent and recovery as every other reply. A run that never finishes is resolved when the reaper records it failed and the next report runs.

## Store lines and the latest run's outcome (2026-11-17)

The head's "Latest completed" line carries that run's duration, compute cost and output (its generated files' size and change, from the run ledger's `secs`, `cost_usd`, `out_bytes`, `delta_bytes`). `nominal.stores` (`{label: store}`) adds one paragraph per store from its root `/api/series`: size and objects at its newest scan, and the change since the newest scan at least a week before (`over Nd`), linked to the store's page. A store whose series can't be read says so (`size unavailable (HTTP N)`); the run outcomes still post. The head is edited whenever this text changes, as before. ## Pinned head and the channel canvas (2026-11-17)

`nominal.pin`: after each report, the open thread's head is pinned in the channel and the head it replaced unpinned (`pin_head`; the pinned ts survives a thread reset in `KEPT`). `nominal.canvas`: the channel's canvas is the deployment's status page (`canvas_text`): the head's first line and a link to the thread, each store, the latest finished run's outcome and five longest phases, the last ten finished runs, and the site's pages; written when its text changes (`write_canvas`: `conversations.canvases.create`, else `canvases.edit` replace; an existing channel canvas is adopted from `conversations.info`). Both join the public channel first (`conversations.join`) and need the app's `channels:join`, `pins:write`, `canvases:write` (`deploy/slack/README.md`): after a manifest update, *Reinstall to Workspace*. They run after the thread converges, so a missing scope logs a report failure and leaves the thread updated.
