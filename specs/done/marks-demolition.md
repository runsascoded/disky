# Marks demolition: retire keep/sweep from the base

**Status: done (branch `marks-demolition`, 2026-09-28).** Shipped in six commits — spec; Functions; site; Python; migrations; this spec moved to `done/`. Verified on the final tree: `pnpm -C site build` (tsc -b, tsc -p functions, vite) clean; `vitest run` 20 files / 182 tests; `cd cloud && uv run pytest -q` 252 passed, 1 skipped; both D1 lineages apply in-memory with the new migration last (`tmp/check_migrations.py`). Rendered against `API_ORIGIN=https://r2.rbw.sh` on :3283: the r2 build's map, children table (no trash — `staging: false`), size chart, diff map, `/users` → `/` redirect, `/staged`; the gcs build's `/`, `/users`, `/assignments`, `/staged` (sign-in / empty data against the r2 API — no runtime error from a missing module). The residual grep (`keep_prefixes|mark_log|mark_totals|MarkState|markAxes|sweep-owners|/api/marks|plan-marks|keep/sweep|set_keep`, excluding `specs/` and `site/migrations/`) is empty; `-w marks` over `site/src`, `site/functions`, `cloud/src` leaves only the `/marks` → home redirect route and the legacy `?c=marks` decode comment.

**Decision (Ryan, 2026-09-28):** the opt-out "mark & sweep" model (keep/sweep marks + a deadline, `specs/sweep-plan-union.md` on `gcs` checkpoint 6 "scope-cut demolition") is retired in favour of the opt-in staged-deletion model already on the base (`specs/staged-delete.md`). "Prod shouldn't have any notion of KLC or marks; certainly the base shouldn't." The KLC kind went first (`f1b51f7`, `a6b4c73`); this removes the keep/sweep mark system entirely — UI, API, Python, and (via new migrations at the end of each D1 lineage) the tables — while keeping the two things that shared code with it: the **owner axis** (attribution: claims/assignments, `/users`, `/user/:id`, `/assignments`, the `o=`/`lens=user:` scopes, owner digests) and **staged deletion** (`/staged`, `/api/plans/*`, both executors and their plan-mode Python).

## Migrations

New files at the end of each lineage; existing files are never rewritten. **Backups are taken** (gcs: `gs://oa-gcs-usage-dvx/backups/marks-backup-2026-09-28.sql.gz`; cw likewise) — only the apply is gated on Ryan.

- `site/migrations/cw/0004_drop_marks.sql` (cw's lineage was rebaselined to `0001_init.sql` + `0002_stage_batches.sql` + `0003_drop_keep_last_ckpt.sql`; `marks`/`mark_log` exist in `0001_init.sql`): `DROP TABLE IF EXISTS marks; DROP TABLE IF EXISTS mark_log; DROP TABLE IF EXISTS marks_new;`
- `site/migrations/gcs/0028_drop_marks.sql` (composes after `0027_drop_keep_last_ckpt.sql`, which is in the lineage but unapplied on prod): `DROP TABLE IF EXISTS` for `marks`, `mark_log`, `marks_new`, `keep_prefixes`, `mark_totals`, `sweep_approvals`; `DELETE FROM actions WHERE set_keep = 1 AND set_owner = 0`; rebuild `actions` without `set_keep`/`keep` (create `actions_new`, copy, drop, rename — SQLite can't drop a column that a CHECK names; `PRAGMA defer_foreign_keys = true` so `owner_prefixes`' references survive the drop/rename inside the transaction), recreate `idx_actions_actor`; `CREATE TABLE owner_totals (scan, head, body, claims, computed_ts, ms, PRIMARY KEY (scan, head))`.

`d1_migrations` rows for earlier (including the squashed-away cw) migration names stay as history; nothing rewrites them.
